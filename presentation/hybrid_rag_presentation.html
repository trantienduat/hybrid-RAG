Project presentation

Hybrid-RAG gives codebase questions two kinds of memory.

Graph structure explains how code is connected. Vector search explains what code means. Local Ollama turns the combined evidence into an answer.

A repository-scoped, Python-first system with reproducible evaluation and explicit safety boundaries.

Open with the user problem: understanding a codebase is not only semantic search. The project combines relationships and meaning while keeping data and models local.
The problem

Code search alone cannot reliably explain execution paths.

Vector-only

Finds language-similar chunks, but can miss callers, inheritance, and dependency edges.

Graph-only

Finds explicit relationships, but does not understand every natural-language question.

Whole-repository prompts

Are noisy, expensive, and difficult to fit into a local model context window.

The design goal: retrieve a small, relevant context that is both semantically close and structurally connected.
Do not claim that one retrieval method is universally bad. Explain the failure modes that motivate the combined design.

Reciprocal Rank Fusion combines independent ranked lists without requiring their raw scores to be comparable.

Point to the two middle branches. The contribution is not inventing graph databases or vector databases; it is integrating them around code-specific retrieval and operational safeguards.
Indexing

Indexing creates complementary views of the same source snapshot.

AST parser → graph. Modules, classes, functions, imports, calls, inheritance, and containment edges become queryable structure.

Source chunks → vectors. Embeddings preserve semantic similarity for natural-language questions.

One provenance boundary. Graph and vectors must agree on source identity, index run, schema, and embedding model.

Scope boundary

Python is the supported semantic language. Java projects are rejected instead of being indexed as if they were supported.

Optional YAML, Markdown, and Dockerfile ingestion is generic document/configuration chunking—not AST-level semantics.

This is an important honesty slide. Unsupported Java is a deliberate fail-closed behavior, not a hidden partial-success path.
Reliability work

The system now fails closed around stale, mixed, or unsafe data.

Repository isolation. Retrieval cannot silently cross namespace boundaries.

Atomic indexing. New data is published before stale data is removed.

Provenance validation. Schema, embedding model, source digest, and index run must match.

Cache invalidation. Response variants and index generations are separated.

Local-only provider. Gemini was removed from scope; Ollama is the enforced provider boundary.

Evaluation guardrails. Missing sources, wrong metadata, or incomplete judge output fail visibly.

Frame these as engineering improvements that make measurements and demos trustworthy. They are as important as retrieval quality.

What is new here?

The contribution is the reliability loop around known techniques.

Known building blocks: hybrid retrieval, graph retrieval, RRF, AST parsing, vector search, and local LLMs.

Project enhancement: combine them for code-specific questions with repository isolation, provenance checks, atomic updates, local-only enforcement, and reproducible answer-quality measurement.

Practical outcome: a developer can inspect why an answer was produced, which source snapshot it used, and whether the benchmark actually completed.

This answer is more credible than claiming a new retrieval algorithm. The novelty is an integrated, operationally reliable system and evaluation discipline.

Code Retrieval with Hybrid-RAG

Combining AST-derived knowledge graphs and semantic search for repository-scoped code questions.

Tran Tien Duat · Master of Software Engineering · 2026

Transcript: This thesis studies code retrieval for questions that cannot be answered by text similarity alone. The system combines semantic search with relationships extracted from Python source code. My goal is not to claim a new retrieval algorithm. It is to show that these techniques can be integrated into a repository-scoped system whose evidence, behavior and limitations are inspectable.

Three questions connect usefulness, cost and evidence strength.

RQ1 · Answer quality: How do Faithfulness, Answer Relevancy and Answer Correctness change versus vector-only retrieval?

RQ2 · Efficiency trade-off: What changes in retrieval latency, local generation latency and token counts?

RQ3 · Evidence strength: Which observed differences remain above or below zero under paired 95% confidence intervals?

Scope: Python semantic indexing · one pinned LlamaIndex Core snapshot · local Ollama · Java rejected explicitly.

A positive average is not enough; the interval determines how strongly the result can be stated.
Transcript: The evaluation asks three connected questions. First, does hybrid context improve the generated answer? Second, what latency and token trade-off accompanies that change? Third, how certain are the observed differences when the same thirty questions are compared as pairs? This framing prevents a positive average from being presented as proof when its confidence interval still includes zero.

System architecture · 05 / 15

One indexed source supports three query-aware retrieval paths.

Running caseBaseRetriever.retrievequery → generic local route

The stores share one source identity; the query path is selected per question.

Parallel graph–vector fusion is one route, not the universal control flow.
Transcript: Indexing creates two complementary representations from the same source identity. It writes the new records before removing stale records and records one provenance identity after the operation succeeds; this reduces empty-index windows but is not a reader-isolated generation cutover. Query analysis then chooses a route. A supported relation question uses a deterministic graph plan and avoids unnecessary vector work when the graph returns a target. A generic local question searches both stores concurrently and fuses their ranks. A global question reads repository-scoped community summaries. This routing is more precise than describing every query as parallel hybrid retrieval.

Retrieval mechanism · 07 / 15

Generic local queries fuse complementary rankings—then select context.

Running caseBaseRetriever.retrievecandidates → RRF → context

RRF merges rank positions; weights vary by route and are not raw-score calibration.

RRF(d) = Σ wₘ / (60 + rankₘ(d))

Generic local: graph weight capped at 1.0, vector weight 1.0 · exact relation: graph-only weight 3.0 · vector-only: (0, 1).

RRF uses rank positions—not raw scores; generic local combines graph 1.0 with vector 1.0.
Transcript: On the generic local route, graph and vector scores are not directly comparable, so RRF uses rank positions instead. The current implementation caps the generic graph contribution at one and gives vector rank weight one, preventing noisy neighborhood expansion from dominating semantic evidence. A successful exact-relation route is graph-only with configured graph weight three. The answer-quality benchmark then keeps the first five fused results and formats them directly; the API also supports optional dynamic token or character budgets, but that path is not what this benchmark measured.

Experimental design · 09 / 15

The confirmatory workload preserves pairing from question to conclusion.

Running caseBaseRetriever.retrieveone representative case · not aggregate proof

The raw-record count is 180; the inferential unit is 30 paired question differences.

Answer model: gemma4:12b · independent judge: qwen2.5-coder:7b · embedding: nomic-embed-text.

180 raw records are retained, but the statistical unit is 30 independent question pairs—not 180 answers.
Transcript: The confirmatory workload has thirty reviewed questions, split evenly across three difficulty levels. Each question runs in vector and hybrid mode three times, giving 180 raw records. For statistics, the repeats are averaged inside each question and mode. The bootstrap then resamples the thirty paired question differences ten thousand times with seed forty-two. This avoids pretending that repeated generations of the same question are independent evidence.

Entity resolution · detail · 2 / 2

Call targets are resolved conservatively, not guessed.

The resolver widens its search only when the previous scope has no unique answer.

Ambiguity remains visible and repository-namespaced instead of creating an arbitrary CALLS edge.
Transcript: A parsed call that cannot be bound immediately is stored as an explicit stub. The resolver first checks a same-class method, then a module-level function in the caller’s module, then an import-aware unique candidate. Remaining stubs are queried against existing graph nodes in one batch and redirected only when exactly one target exists. Ambiguous or missing targets remain namespaced stubs, preserving uncertainty rather than inventing structure.

Paired bootstrap · detail · 3 / 3

The analysis resamples questions, not repeated generations.

For each case and mode, average the three repeated generations.
Compute Hybrid minus vector for the same thirty questions.
Sample thirty question indexes with replacement, 10,000 times.
Report the 2.5th and 97.5th percentiles as the paired 95% interval.
The checked-in analysis is deterministic with seed 42 and reproduced byte-for-byte during this audit.
Transcript: The three runs of one question are repeated measurements, not three independent questions. The analysis first averages those repeats inside each case and mode. It then resamples the thirty paired cases ten thousand times. For each sample it computes the hybrid-minus-vector mean. The outer two-and-a-half percent on each side form the confidence interval. Seed forty-two makes the output deterministic, and the generated statistics file reproduced exactly during verification.
